3. PRODUCT: SNAPDESK ("customer support that can see")
-------------------------------------------------------
3.1 Problem: most support problems are solved with visual evidence (crushed parcel, cracked screen, faulty appliance, wrong item, leaking/flickering device). Today a human opens each photo or video clip, judges it, checks the refund policy and types a reply. Slow, expensive, and the main reason refunds/claims drag for days.
3.2 Solution: a business signs up, defines its policy, and gets a support link. A customer sends photo(s) or a short video clip + a short message (text or voice) + order value. Snapdesk (a) measures and tracks the damage in the photo or video with SAM 3.1, (b) applies the business's own policy with Muse Spark, (c) runs plain-code guardrails that force a human handoff when it should, (d) replies to the customer and (e) produces an EVIDENCE PACKET (annotated photo/video frames, measurements, decision, cited policy clause, timeline).
3.3 Key idea to protect: THE POLICY IS THE ONLY CONFIGURATION. The same product serves parcel damage, appliance triage, rentals, insurance claims by swapping a policy template (rules + text + SAM prompts). The demo must prove this.
3.4 Design principle: THE MODEL NEVER HAS THE FINAL SAY ON MONEY. Deterministic guardrails override the model.
3.5 Business model (do not overclaim): usage-based pricing per resolved case, free allowance. Buyer saves the cost of a person handling each photo ticket; faster resolution, fewer disputes. No customers/revenue exist; never claim them.
3.6 Non-goals: no model training/fine-tuning; no payments; no user accounts/auth (unless time remains); no real refunds executed; no medical content.

4. META MODELS AND API REFERENCE (Meta Model API, "Model API")
--------------------------------------------------------------
4.1 Common
- Base URL: https://api.meta.ai/v1. Auth: Bearer token = env var MODEL_API_KEY (create at https://dev.meta.ai/ -> API keys). Key format looks like LLM|{id}|{secret}.
- Drop-in compatible with the OpenAI SDK (also Anthropic Messages). The OpenAI SDK does NOT auto-read MODEL_API_KEY: always pass apiKey explicitly. new OpenAI({ baseURL: 'https://api.meta.ai/v1', apiKey: process.env.MODEL_API_KEY }).
- Errors: 401 invalid_api_key; 404 model_not_found (use exact ids). Back off with jitter on retryable errors (see cookbook 01_api_fundamentals/09).
4.2 SAM 3.1 (model id "sam-3.1") - USED FOR VISION
- Open-weight Meta model hosted on Model API. Give a SHORT NOUN PHRASE + image (or video); returns a box and pixel-accurate mask for every match; in video it tracks objects across frames. Can also segment from box/point prompts.
- Request (Responses API, streamed): client.responses.create({ model:'sam-3.1', stream:true, input:[{ type:'message', role:'user', content:[ {type:'input_text', text:'cardboard box'}, {type:'input_image', image_url:'data:image/jpeg;base64,...'} ] }] }).
- ONE concept per request. For several concepts, issue separate requests and combine in application code.
- Decode with the official parser package @meta-sam/parser (npm; cookbook pins ^0.0.10): parseImageStream(events).finalResult, recordsOfKind(result.records,'mask'|'box'), decodeMaskToRaster(mask) (array of 0/1, mask.width x mask.height), decodeMaskToSVGPath(mask). Check result.outcome.status==='completed'. Never parse the text grammar by hand.
- The API streams response.content_part.done but not response.output_text.done; the cookbook's normalizedEvents() helper synthesizes it (copy it with attribution to the MIT-licensed cookbook).
- Video: upload via client.files.create({file, purpose:'user_data'}) -> file id 'file-...', then content item {type:'input_video', file_id}. Cumulative snapshots, final result holds full history.
- Pricing (public listing, verify): about $2.50 per 1,000 images, $0.20 per 1,000 video frames.
4.3 Muse Spark (model ids "muse-spark-1.3" recommended, "muse-spark-1.2", "muse-spark-1.1") - USED FOR DECISIONS, REPLIES, SUMMARIES
- Multimodal reasoning/agentic model. Input: text, image, video, audio, PDF; output text; 1,048,576-token context; tool calling (parallel), structured output, reasoning effort levels, prompt caching, search grounding.
- APIs: Responses (POST /v1/responses), Chat Completions (POST /v1/chat/completions), Messages (Anthropic format).
- STRUCTURED OUTPUT (Chat Completions): response_format = { type:'json_schema', json_schema:{ name:'snapdesk_decision', schema:{ type:'object', properties:{...}, required:[...], additionalProperties:false } } } -> JSON.parse(choices[0].message.content). (Cookbook 01_api_fundamentals/04.)
- VISION INPUT: Chat Completions content parts [{type:'text',text}, {type:'image_url', image_url:{url:dataUrlOrHttpUrl}}] in USER messages (images in a 'developer' message return HTTP 400). Responses API content parts: {type:'input_text'} and {type:'input_image', image_url}. Token counting: POST /responses/input_tokens. (Cookbook 01_api_fundamentals/07.)
- Spark 1.3 audio input is degraded: use Muse Voice Transcribe for speech.
- STANDARD vs CONTRIBUTOR MODE: Standard ids (muse-spark-1.3) = content NOT used to train Meta models. Contributor ids (muse-spark-1.3-contributor) = cheaper, but Meta MAY TRAIN on content. Customer photos/messages => ALWAYS USE STANDARD IDS. Muse Code subscriptions default to Contributor (we are not using Muse Code).
- Pricing (third-party listings, verify in billing): about $1.25 input / $4.25 output per 1M tokens. The cookbook says the preview is free: check dev.meta.ai pricing/credit terms.
4.4 Muse Voice Transcribe (model "muse-voice-transcribe-1.0") - USED FOR VOICE COMPLAINTS
- Speech-to-text only (no TTS). 25 languages with code-switching, speaker diarization, endpointing, turn-level timestamps (no word-level). About $0.18 per hour.
- File endpoint: POST https://api.meta.ai/v1/asr/transcribe (recording you already have). Realtime: wss://api.meta.ai/v1/asr/realtime (WebSocket, partials are cumulative, final:true frame ends).
- Input: mono 16-bit WAV at 24 kHz (native) or 16 kHz. Convert: ffmpeg -i in.mp3 -ac 1 -ar 24000 -sample_fmt s16 out.wav. (Cookbook 06_muse_voice/01_voice_api_fundamentals: transcribe_file.py, transcribe_stream.py, utils.py.) Prefer the FILE endpoint for voice notes.
4.5 Muse Image (model "muse-image-1.0"): NOT AVAILABLE IN INDIA (Geographic Use Policy, effective Oct 12, 2026). DO NOT USE. Evidence images are drawn in code from SAM masks.
4.6 Muse Wonder (model "muse-wonder-1.0", preview): Meta's most capable model for long agentic/coding work; costs more; same requests as Spark. Not planned (Spark is cheaper and enough).

5. END-TO-END FLOW (ONE CASE)
-----------------------------
1) Customer opens the support link, uploads 1-3 photos or a video clip, types or records the problem, enters order value. 2) Server hashes the visual media (duplicate detection) and, for voice, transcribes via Muse Voice Transcribe. 3) SAM 3.1 segments/tracks: the product, each damage phrase, and contents-damage phrases across photo or video frames; code converts masks to numbers. 4) Muse Spark receives policy text + numeric rules + measurements + customer message and returns strict JSON (decision, clause, reasons, confidence, missing_info, reply). 5) Guardrails (plain code) may override to HANDOFF. 6) Outcome: AUTO (customer gets the reply) or HANDOFF (a human gets photo/video evidence, measurements, flags and a drafted reply/summary). 7) Evidence packet generated and stored. 8) Business reviews cases and can edit the policy; the next case follows the new rules.
To make this a real AGENT (judges penalize plain analyzers), structure the pipeline as visible steps/tool calls: measure -> check duplicate -> check policy -> check value/confidence -> decide or escalate -> draft reply -> build evidence. Show these steps in the UI/demo (an "agent trace").

6. THE SEVEN SECTIONS (each built and tested on its own)
--------------------------------------------------------
SECTION 1 - INTAKE (customer side)
- Purpose: the support link where a customer submits a case. Inputs: 1-3 images or short video clip (data URLs / files), message, order value, policy/template id. Duplicate detection by SHA-256 of visual media bytes.
- Meta: Muse Voice Transcribe for voice notes (file endpoint, WAV mono 16-bit).
- Status: NOT BUILT.
- Acceptance: a customer can submit photo(s) or video + text/voice from a phone browser and get a result.
SECTION 2 - VISION (measure the damage)
- Purpose: find the product and the damage and turn masks into numbers. Policy template supplies SAM phrases: product ("cardboard box"), damage (["crushed corner","torn cardboard"]), contents (["broken item"]). Measurements: damaged area as share of the product mask, region boxes/masks, contents_damaged boolean, product_found boolean. Cache SAM results per image hash+phrase.
- Meta: SAM 3.1 only. Stretch: small open-weights model checks photo usability first (blur/irrelevant) to save credits.
- Status: NOT BUILT. Start from meta-model-cookbook/07_sam/01_api_basics.
- Acceptance: on real damage photos the overlay lands on the damage; area ratio is plausible; failures are handled (no product found => handoff).
SECTION 3 - DECISION ENGINE
- Purpose: apply the business's policy to the measurements and message. Output strict JSON (section 7.3). Reply in the customer's language.
- Meta: Muse Spark 1.3 (Standard), json_schema structured output. Possible upgrade: send the image too (image_url) so Spark double-checks contents damage; and use tool calls for the agent trace.
- Status: NOT BUILT.
- Acceptance: valid JSON every time; cites a real clause from the policy; chooses handoff when the policy is silent.
SECTION 4 - GUARDRAILS AND HANDOFF
- Purpose: deterministic override. Force HANDOFF on: duplicate_photo, low_confidence (< rules.min_confidence), high_value_order (> rules.handoff_order_value), missing_info, product_not_found, model_requested_handoff. Handoff gives a human the photo, measurements, flags and a short written summary.
- Meta: none for the rules (plain code on purpose). Muse Spark writes the handoff summary (TO DO).
- Status: NOT BUILT.
SECTION 5 - EVIDENCE PACKET
- Purpose: a clean record per case: annotated photo (real SAM mask path drawn as SVG overlay + box + label + area %), measurements, decision with flags, cited clause, timestamp, timeline text.
- Meta: SAM masks rendered in code (NO Muse Image); Muse Spark writes the timeline text (TO DO).
- Status: NOT BUILT. (Export to PDF/PNG is optional.)
SECTION 6 - POLICY AND TEMPLATES (business side)
- Purpose: the business edits rules/text; swapping templates changes the product with no code change. Templates: parcel-damage (first), appliance-triage (second), vehicle-damage (if time). Planned: paste plain-text policy and let Muse Spark produce rules JSON + SAM phrases (validate with a schema before saving).
- Meta: Muse Spark (policy text -> rules/prompts).
- Status: NOT BUILT.
- Demo moment: change a threshold and re-run the SAME photo so the decision flips.
SECTION 7 - CASE LIST AND PROOF
- Purpose: list cases, auto-vs-handoff rate, and measured accuracy versus human rulings on the project's own photo set. Dashboard is SECONDARY (anti-project warning). No Meta model.
- Status: NOT BUILT.

7. DATA CONTRACTS
-----------------
7.1 Policy template (policies/<id>.json)
{ "id":"parcel-damage", "name":"Parcel damage", "text":"<plain-language policy>",
  "rules":{ "refund_if_contents_damaged":true, "packaging_replace_max_ratio":0.3, "handoff_order_value":200, "min_confidence":0.7 },
  "prompts":{ "product":"cardboard box", "damage":["crushed corner","torn cardboard"], "contents":["broken item"] } }
7.2 Measurements (planned output of the vision step)
{ mock:boolean, product_found:boolean, contents_damaged:boolean, packaging_damage_ratio:0..1,
  regions:[{ label, area_ratio:0..1, bbox:[x,y,w,h] normalised 0..1, mask?:{ path:<SVG path>, w, h } }] }
7.3 Model decision (planned output of the decision step)
{ decision:"refund|replace_packaging|replace_item|handoff", clause:string, reasons:string[], confidence:0..1, missing_info:string[], reply:string }
7.4 Guardrail result: { final:<decision or "handoff">, model_decision, flags:string[] }
7.5 Case (stored in memory): { id, createdAt, measurements, model, final, model_decision, flags } plus the image data URL kept server-side for the evidence packet.
